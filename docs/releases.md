# Versioned releases

The public Releases menu opens `/releases/`. Each entry contains its version,
release date, short change notes, package size, checksum and original ZIP download.
The archive starts at v0.6.0. Earlier development builds are not reconstructed.

## Create a release

After implementing and testing a core functionality change, run:

```sh
python tools/manage_releases.py create --bump patch --title "Fix tool outcome validation" --change "Corrected validation of failed tool outcomes."
python tools/manage_releases.py check
```

Choose `--bump minor` for new functionality or `--bump major` for incompatible
changes. Use repeated `--change` arguments for multiple notes. An explicit
`--version 0.7.0` is also supported. `--date YYYY-MM-DD` selects a specific release
date; otherwise the host's current date is used.

The command updates `VERSION`, appends an entry to `web/releases.json`, renders
`web/releases.html` and creates a new ZIP under `web/downloads/releases/`.
Commit these together with the implementation when ready. It does not commit,
push, create Git tags or publish a GitHub Release on its own.

Each ZIP includes VERSION and RELEASE_NOTES.md, the console runtime, supported
integration examples and library packs. Runtime databases, credentials and model
weights are excluded. Previous ZIPs are never regenerated by the website build.

Pages and evaluation workflows verify archive checksums, catalog ordering and a
fingerprint of core sources. A core change without a new version fails the check;
it does not automatically invent a version or change description. Future coding
agents are instructed to create the release as part of completing core changes.
Documentation and marketing changes alone can be published without a core bump.

## Publish and retain downloads

Push the new version files and code using your normal Git process. The Pages
workflow publishes all cataloged downloads, preserving their original bytes and
making the latest archived package the default static download.

For counted GitHub Release downloads, the existing Publish download packages
workflow accepts the corresponding tag, such as `v0.6.0`, only when it matches
VERSION. It publishes the frozen console archive with the recorded change notes;
existing GitHub releases are not replaced. Historical downloads also remain
available through the static Releases page.

Local source and Elastic Beanstalk deployments serve `/releases` too. The minimal
console download links its guide navigation to the public Releases page rather
than embedding old ZIPs inside new ones. This avoids recursive archives.

Back up the console database before upgrading. Archived code does not include
saved user data. Older versions may not support newer database/configuration
formats; use an isolated copy of data when evaluating a downgrade.
